# STEP 4 검증 기록

## 구현 범위

60개 검수 미션과 필터링 → 최근 노출 제외 → 가중치 → 단일 추첨을 구현했습니다.
기존 미션 16개 ID와 저장 버전 1, 화면 흐름을 유지합니다.
새 템플릿은 동행별 파일에 11개씩 나눴고 모든 템플릿을 Zod로 검증합니다.
안전 규칙은 모든 강도에 동일하게 적용하며, 실제 신체 활동량도 에너지 상한에 포함합니다.

## 자동 검증

`npm run check`: 포맷 → ESLint → 타입 → Vitest → production build.
기존 25개에 추천·데이터 테스트를 추가해 총 66개입니다.

- 60개 ID·제목 고유성, 기존 ID 유지, 12개 카테고리, 동행별 후보 15개 이상
- 무료 25개 이상, 집 미션 20개 이상, 술·운전·신체 위험 미션 없음
- 7,680개 입력 조합 각각의 낮(12시)·밤(23시) 추천 가능성과 조건 일치: 15,360건
- 야간 경계 23시/06시, 시간 불명·잘못된 입력 차단, 가족·인원·이동 범위
- 최근 5개 서로 다른 ID 제외, 같은 시각의 노출과 정렬되지 않은 기록 처리
- 후보 소진 시 오래된 노출부터 재허용, 현재 미션·안전·예산 조건 유지
- 미완료 가중치 1.8, 카테고리 0.6~1.4, 강도 1.0~1.5
- 최신 명시적 선호 우선, 피드백·세션 중복 집계 방지, 최근 완료 40회만 반영
- 명시적 선호 없는 별점 처리, 무관한/완료되지 않은 미션의 피드백 제외
- 신규 요청과 재추천에 저장된 피드백 전달
- 누적 확률 경계, 균일한 400개 표본에서 1:2:1 가중치의 100:200:100 선택
- 빈 풀에서 추첨 없음, 잘못된 랜덤값·가중치·합계 오버플로 거절

확률 테스트는 `Math.random`에 의존하지 않고 고정된 표본을 주입해 재현합니다.

## 브라우저 확인 절차

1. 기존 질문·진행·완료 기록이 새로고침 후 유지되는지 확인합니다.
2. 낮은 에너지·0원·15분·집에서만 조건으로 추천하고 여러 번 다시 고릅니다.
3. 한 번에 하나만 나오고 현재 미션을 바로 다시 보여주지 않는지 확인합니다.
4. 친구/연인/가족으로 동행을 바꿔 해당 관계에 맞는 미션인지 확인합니다.
5. 새 미션을 수락하고 체크리스트·완료 입력·결과·다음 추천까지 확인합니다.
6. 390px 모바일의 가로 넘침과 브라우저 오류를 확인합니다.

선호와 확률 영향은 단위 테스트로 검증합니다. 화면 한 번의 추천으로 확률 변화를 판단하지 않습니다.

이번 검증은 프로덕션 서버를 별도 포트에서 실행해 기존 개발 origin의 기록과 분리했습니다.
기존 추천·완료 기록 복원, 가족/15분/0원/집/에너지 1/인생은 한 번 조건을 확인했습니다.
거절 사유 선택 후 3회 재추천에서 현재 미션의 즉시 반복이 없었고, 모든 결과가 조건을 유지했습니다.
PLAY의 체크 1/3 복원 → 전체 체크 → 평가·좋아요·코멘트 입력 → 완료까지 확인했습니다.
완료 후 새로고침에도 누적 EXP 200과 완료 수 2가 유지됐고, 다음 추천에 새 seed인
`가족 간식 취향 투표`가 표시됐습니다. 모바일 가로 넘침과 브라우저 오류·경고는 없었습니다.

## 한계와 다음 단계

시간대는 기기의 현지 시간을 사용합니다. 실제 지도·날씨·영업시간·상품 가격 조회는 없습니다.
장소 미션은 설명의 조건 안에 이용 가능한 곳이 있을 때 수행하며,
이용할 수 없으면 재추천할 수 있습니다. 선택 사유만으로 비용·시간 상한을 자동 변경하지 않습니다.
추천 엔진은 LLM·네트워크·저장소에 의존하지 않는 함수이며,
Supabase에서 검증된 템플릿과 소유 기록을 주입하도록 STEP 5에서 연결합니다.
