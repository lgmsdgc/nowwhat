# NowWhat — STEP 1 설계 / STEP 4 가중 추천

## 원칙

- 사용자의 상황으로 지금 할 행동 하나만 결정한다.
- 로그인 없이 시작하고 완료 후 기록 저장을 제안한다.
- 검수한 템플릿 + 필터링 + 가중 무작위 추첨을 사용한다. LLM은 필수 의존성이 아니다.
- UI와 비즈니스 규칙, 데이터 저장을 분리한다.
- 기본 MVP에서 지도, 실제 매장, 실시간 영업시간, 결제, 그룹, 피드를 구현하지 않는다.

## 화면과 구조

`/` → `/onboarding` → `/mission/[sessionId]` → `/play/[sessionId]` → `/complete/[sessionId]`

`/profile`, `/auth`, `/auth/callback`은 이후 단계에서 추가한다.

- app: 라우팅, 메타데이터, 페이지 구성
- components: 공통 UI와 레이아웃
- features: 각 화면과 사용자 입력
- services: 추천, 수락, 시작, 완료, 포기, 피드백의 작업 순서
- lib: 추천/안전/보상 규칙, 저장소, 입력 검증, 외부 서비스 연결
- types: 도메인 모델, data: 선택지와 정책 상수, seed: 검수된 미션/칭호

## 입력과 추천

동행, 시간, 1인당 예산, 이동, 에너지, 원하는 강도: 총 6단계.
무제한은 null. 2~3시간은 최대 180분, 반나절은 최대 360분.
에너지는 신체 활동량의 상한, 강도는 낯섦과 도전의 선호도다.

검증 → 안전 필터 → 수행 조건 필터 → 최근 노출 제외 → 가중치 → 하나 추첨.
예산/시간은 템플릿 상한을 기준으로 검사한다. 실내 장소와 집은 구분한다.
인원 수를 묻지 않는 MVP에서는 정확한 인원이나 특수 준비물에 의존하는 템플릿을 제외한다.

23~06시 야간 안전, 혼자/가족 안전, 미성년자 안전을 확인한다.
위험/불법/무단 침입/개인정보 공개/타인 피해/음주/차량 운전 미션은 초기 후보에서 제외한다.
모든 강도에 같은 안전 기준을 적용하고 시작 때도 시간대 조건을 다시 확인한다.
후보 소진 시 오래된 노출 제외만 완화한다. 비용/시간/안전은 완화하지 않는다.

초기 가중치: 미완료 1.8, 완료 1.0, 카테고리 선호 0.6~1.4, 강도 근접 1.0~1.5.
최근 5개 서로 다른 미션과 현재 미션을 제외한다. 후보가 없으면 가장 오래된 노출부터 허용한다.
현재 미션과 안전·시간·예산·동행·활동량 상한은 계속 유지한다.
60개 seed 목표: 동행별 15개, 집 20개 이상, 무료 25개 이상(중복 집계).

## 데이터와 상태

profiles, missions, mission_relationships, mission_sessions,
recommendation_feedback, achievements, user_achievements, analytics_events.

템플릿과 실행 기록을 분리하고 세션에 템플릿 버전/내용/입력 스냅샷을 남긴다.
recommended → accepted → started → completed 또는 abandoned.
recommended → rejected 후 새 세션. recommendation_run_id와 reroll_index로 재추천을 추적한다.
실제 비용 미입력과 0원을 구분한다. 시간은 started_at / completed_at으로 계산한다.
완료/EXP/칭호는 한 트랜잭션으로 처리하고 중복 요청을 무해하게 만든다.
초기 보상은 완료당 100 EXP, 300 EXP마다 레벨 상승. 난이도별 보정은 정책으로 분리한다.

## 익명과 보안

STEP 3은 localStorage와 anonymous_id. STEP 5는 Supabase 익명 Auth로 소유권을 확립한다.
DB의 소유권은 검증된 auth.uid()로 검사한다. anonymous_id만으로 접근/이관하지 않는다.
Google/Email 연결과 기존 계정 병합은 분리하고, 소유권 검증/재시도/중복 제거를 적용한다.
로컬 기록은 검증/출처 기록을 거쳐 이관하고 EXP/레벨을 클라이언트 값으로 덮어쓰지 않는다.
RLS를 활성화하고 보상/칭호와 템플릿 쓰기는 서버에 한정한다.
AI는 미션 조건을 바꾸지 않고 표현 보정만 수행한다. 실패 시 템플릿 원문을 사용한다.

landing_view, onboarding_started, onboarding_completed, mission_requested,
mission_shown, mission_rejected, mission_accepted, mission_started,
mission_completed, mission_abandoned, mission_shared.

event_id, 방문 ID, 사용자 ID, 추천 흐름 ID, 세션 ID, 현지 날짜/발생 시간을 연결한다.
수락률, 완료율, 재추천 횟수, D1 재방문, 완료 후 공유율을 계산한다.
공유 클릭과 실제 공유 성공을 구분하며 개인 코멘트/비용을 자동 공개하지 않는다.

## STEP 3 구현 상태

6단계 온보딩과 단일 추천, 수락과 동시에 시작하는 PLAY, 완료 입력과 EXP 결과를 연결했다.
수락과 시작은 같은 시점에 두 타임스탬프를 저장하며 세션 상태는 `started`가 된다.
STEP 3 시점에는 16개 mock 템플릿과 수행 가능성 필터·균등 추첨을 사용했다.
가중치와 60개 seed는 STEP 4에서 추가했다.

localStorage 문서를 Zod로 검증하고 Web Locks로 탭 간 명령을 직렬화한다.
완료·보상·피드백은 하나의 쓰기로 기록한다. 로컬 EXP는 완료 세션에서 합산하며,
완료 재요청은 같은 결과를 반환한다. 시간·체크·완료 입력·질문 단계는 새로고침 후 복원한다.
프로필·칭호·인증·서버 보상·분석 수집은 아직 연결하지 않았다.

## STEP 4 구현 상태

원래 16개 ID를 유지하고 동행별 11개씩 추가해 60개 seed를 구성했다.
12개 카테고리를 포함하며 집·무료·낮은 에너지·밤 조건에도 후보가 있다.
실제 장소·가격·운영시간은 API로 조회하지 않으며, 장소 미션의 첫 단계에서
사용자가 이용 가능 여부와 왕복 시간·비용을 확인한다.

가중치는 `미완료 여부 × 카테고리 선호 × 강도 근접도`로 계산한다.
선호는 최근 완료 40회에서 최신 좋아요/싫어요를 세션마다 한 번만 집계한다.
명시적 선택이 없으면 재미 4~5점/1~2점을 긍정/부정으로, 3점·미입력은 중립으로 처리한다.
카테고리 점수는 1에서 표당 0.1씩 바뀌고 0.6~1.4로 제한한다.
강도는 거리 0~3을 1.5~1.0으로 변환하고 `아무거나`는 1이다.
`편안하게`는 강도 1만 후보로 허용하며, 다른 강도는 다양한 후보의 양수 확률을 유지한다.

후보와 가중치 요소를 반환하는 함수와 실제 누적 확률 추첨 함수를 분리했다.
15,360개 상황 조합, 중복 선호, 후보 소진, 추첨 경계와 확률 비율을 검증했다.

## STEP 5 구현 상태

local 모드를 기본으로 유지하고 명시적인 supabase 모드를 추가했다.
브라우저 익명 Auth, 서버 getUser 검증, 7개 테이블·60개 SQL 시드·RLS를 구성했다.
서버는 명령만 받아 DB 기록·템플릿·서버 시간으로 상태를 계산한다.
서버 전용 commit RPC는 프로필 잠금과 revision 검사 후 세션·피드백·EXP를 원자적으로 저장한다.
DB 오류를 로컬 성공으로 대체하지 않으며, 모드 전환으로 로컬 기록을 자동 이관하지 않는다.

프로젝트가 없는 환경에서 실제 PostgreSQL(PGlite)로 SQL·RLS·권한·롤백·중복 완료를 검증했다.
호스팅된 Supabase Auth/PostgREST 연결은 프로젝트 준비 후 확인해야 한다.
회원가입·계정 연결·기록 이관은 STEP 6, 칭호 데이터와 획득 판정은 STEP 7에 남아 있다.
연결 절차와 데이터 구조는 `docs/supabase-setup.md`에 정리했다.

## STEP 6 구현 상태

완료 2회 후 저장 안내, Google/Email 가입·로그인, PKCE callback과 계정 화면을 연결했다.
새 가입은 익명 사용자 ID에 identity를 추가하고 기존 기록·EXP를 유지한다.
기존 계정 로그인은 익명 소유권으로 발급한 일회용 증명과 로그인한 회원 ID를 함께 검증해 이관한다.
트랜잭션으로 세션·피드백·EXP를 합치고 중복 이관·재지급을 방지한다.
진행 중 미션 충돌은 목적지를 유지하고 source를 보상 없이 종료한다.

localStorage 완료 기록은 명시적 선택 후 `local_mission_history`에 source와 함께 보관한다.
서버가 증명할 수 없는 로컬 EXP는 지급하지 않고 원본도 삭제하지 않는다.
계정 전환 시 이전 화면 데이터·대기 명령·응답을 적용하지 않는다.
112개 자동 테스트와 로컬 모바일 화면을 검증하며 원격 Google/Email 연결은 프로젝트 준비 후 확인한다.
설정·이관 정책은 `docs/account-setup.md`에 있다. 프로필·칭호 확장은 STEP 7에 남아 있다.

## STEP 7 구현 상태

`/profile`에 완료 수·총 EXP·레벨 진행도, 칭호 9개와 진행 상황,
최근·좋아한·아쉬운 미션 필터를 추가했다. 계정 연결은 `/account`로 이어진다.
완료 화면은 이번 완료에서 얻은 칭호와 프로필 링크를 보여준다.

새 템플릿 보상은 난이도 1~5별 100/120/140/160/180 EXP로 정하고
추천 시 스냅샷에 고정한다. 300 EXP마다 레벨이 오른다. 기존 보상을 재계산하지 않는다.
로컬 칭호는 기존 v1 완료 기록으로 최초 획득 시각·세션을 복원한다.
DB는 완료 트리거와 프로필 잠금으로 완료·EXP·칭호를 원자적으로 저장한다.
계정 이관 시 합쳐진 기록도 검사하며 로컬 보관 기록은 보상에 포함하지 않는다.

칭호 조건은 완료 수와 서로 다른 카테고리 수에 카테고리·동행·야외·실제 0원 필터를 조합한다.
같은 조건 유형의 새 칭호는 DB 정의 추가만으로 조회·지급·표시된다.
새 조건 유형은 TypeScript·SQL 검증과 판정을 함께 추가한다.
136개 자동 테스트와 production build를 통과했고, 실제 원격 Supabase 검증은 프로젝트 준비 후 진행한다.

## STEP 8 구현 상태

방문·페이지·추천 요청·공유는 브라우저에서, 미션 노출·거절·수락·시작·완료·포기는 저장된 상태 전환에서 기록한다.
방문 ID는 탭의 sessionStorage에 보관하며 새로고침을 견디고 30분 비활동 후 바뀐다.
이벤트 ID와 의미별 중복 키를 함께 사용한다. 요청 시도와 성공한 추천 노출을 구분한다.

로컬 분석은 v1 문서에 최대 2,000개를 보관한다. DB 모드는 최대 300개 전송 큐를 20개씩 보낸다.
게임 전환 이벤트는 서버 트리거가 확정하며 사용자 제출로 위조할 수 없다.
분석은 best effort이며 실패해도 게임·EXP를 우선한다. 원격 계정 이관은 이미 저장된 분석 소유자도 연결한다.

세션 기준 수락률·완료율, 사용자/추천 흐름별 재추천, 현지 날짜 기준 관찰 완료 코호트의 D1을 집계한다.
완료 화면에 공유와 링크 복사를 추가하고 채널을 분리한다. 개인 코멘트·비용·세션 주소는 포함하지 않는다.
집계 함수·비공개 조회 API·JSON 리포트 CLI를 제공하며 공개 대시보드나 외부 분석 SDK는 추가하지 않았다.
수집 한도·과거 데이터·공유 성공의 한계는 `docs/analytics-setup.md`에 정리한다.

## 재추천 UX 변경 — 2026-10-07

`한 번만 다시`는 이유 선택 없이 즉시 재추천한다. 기존 거절 사유는 보존하고 새 거절은 사유 null로 기록한다.
재추천 횟수·추천 흐름·분석 이벤트는 계속 기록하며 처리 중 중복 클릭을 막고 실패 시 기존 미션과 오류 안내를 유지한다.
